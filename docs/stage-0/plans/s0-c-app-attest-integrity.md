## Kill-risk question

Can one Hezo Link installation on a supported physical iPhone complete environment-separated App Attest registration and request-bound assertions, reject every malformed, substituted, replayed, stale, or cross-environment input with atomic counter protection, degrade safely when integrity is unavailable, and authorize a downstream operation without forwarding an App Attest or stable installation identity?

The answer is negative if the full Apple validation chain cannot be implemented independently and boundedly; a physical development flow or internal TestFlight production flow cannot complete; an invalid input, replay, counter rollback, body swap, or environment mix-up is accepted; an unavailable integrity path makes the synthetic manual-route eligibility sentinel ineligible or gives an untrusted report security weight; capability recovery cannot be made single-use and deterministic; or any App Attest material, stable subject, semantic request body, or joinable replay identity reaches intelligence, MPD, analytics, URL Filter runtime state, general telemetry, or support tooling.

A negative answer pauses App Attest-backed report influence, measurement authorization, filter-token bootstrap, and any other integrity-required write path. It does not make the accountless, reduced-trust manual-route eligibility sentinel ineligible; that sentinel is not proof of a working manual read product. The negative answer cannot be compensated for by weakening replay, counter, environment, identity-stripping, or semantic validation rules.

## Scope

### In scope

- A minimal containing-app proof client and isolated proof verifier, with no consumer UI or product framework.
- One authorized physical-device development flow using development-only App Attest state.
- One restricted internal TestFlight flow proving Apple's production App Attest environment against production-only proof state.
- A frozen Hezo challenge, client-data, canonical-request-digest, registration, assertion, capability, idempotency, error, reduced-trust, and retention contract.
- Complete bounded attestation, receipt, assertion, counter, replay, concurrency, environment, lifecycle, and failure validation.
- A verifier-independent oracle or implementation and governed mutation fixtures whose raw Apple/security artifacts remain outside Git.
- A synthetic downstream consumer proving audience, purpose, exact-request, expiry, replay, and identity-stripping behavior.
- Negative data-flow, log, trace, support, export, backup, and cross-plane join tests.
- Teardown and separately authorized productionization closeout paths.

### Out of scope

- Product application scaffolding, consumer UI, production APIs, production verifier or database, production deployment, production traffic, or production credentials.
- URL Filter, Bloom, PIR, Privacy Pass, provider, verdict, sandbox-crawler, MPD, analytics, and report-product implementation.
- O-005 accountless PIR token or O-018 PIR protocol-state decisions unless a later approved revision explicitly adds the S0-B handoff cases and prerequisites.
- App Store release, external TestFlight/public beta, marketing or privacy-policy approval, or closure of O-010.
- Selecting a backend language, framework, package manager, parser, crypto library, cloud, KMS, database, queue, observability vendor, CI runner, or proof repository root.
- Treating Apple's optional fraud-risk metric as identity, MPD, deduplication, or sole authority for denial or enforcement.
- Depending on iOS 27-only validation-category or bundle-version fields for the iOS 26 product floor.
- Legacy DeviceCheck per-device bits or tokens.
- Committing real or fake attestation/assertion CBOR, certificates, receipts, key IDs, capabilities, signing/JWT material, device output, or Apple identifiers.

### Assumptions and unknowns

- The containing iOS app can use App Attest on the approved physical device and signing configuration. `isSupported == false`, entitlement/signing rejection, or physical inability to complete registration falsifies this assumption for that matrix cell.
- TestFlight forces production App Attest behavior, but it does not turn Hezo's disposable proof verifier, stores, routes, data, or credentials into production infrastructure. Any dependency on a Hezo production route, credential, or dataset stops the proof.
- Apple's complete supported-extension lists currently conflict, but no current source includes a URL Filter Network Extension. Hezo's proof boundary is therefore firm: only the containing app invokes App Attest; the universal extension list remains unresolved.
- Apple currently documents two development AAGUID labels. The approved sandbox verifier may recognize only the exact encodings justified by the frozen release/device matrix; production remains exact and must never inherit sandbox tolerance.
- An actual App ID prefix may differ from the 10-character Team ID. The verifier freezes both restricted values from their distinct authoritative configuration sources: the attestation RP ID uses the profile-evidenced App ID prefix plus bundle identifier, while receipt field 2 uses the Team ID plus bundle identifier. One configuration field may not be sourced from the other. If their bytes happen to be equal, provenance—not an impossible byte-level substitution test—proves the semantic separation. A definitive contrary physical observation is Stop. A permitted source contradiction is Inconclusive only when it leaves the required observation genuinely undecidable with no observed failure. Neither outcome creates a tolerant dual interpretation.
- Valid iOS 26 material may omit newer validation-category and bundle-version extensions. Presence must be parsed strictly; absence remains valid for iOS 26.
- Every initial attestation receipt must be validated. The later Apple fraud-risk redemption/refresh service is optional and needs a pre-run scope decision.
- Subjectless direct capabilities reduce downstream identity exposure but retain timing-correlation limits. S0-C cannot claim cryptographic unlinkability or substitute them for a blinded measurement credential.
- A temporary Apple or TestFlight outage can make an authorized live run Inconclusive. Missing authority, fixtures, contracts, devices, or evidence before execution leaves the plan Draft instead.

## Environment and isolation

### Class A — offline contract and parser preparation

- Technically deny all network and private-file access.
- Use only governed public synthetic vectors or generated-in-memory restricted fixtures inside the approved proof boundary.
- Pin contract, parser, crypto, independent oracle, generator, schema, and fixture revisions and digests.
- Apply exact byte, depth, item, time, memory, concurrency, and mutation bounds.
- Reset every challenge, key, counter, receipt, capability, replay, log, and cache store between isolated subruns.
- This class can prove deterministic parsing and state-machine behavior; it cannot prove Apple service, Secure Enclave, device, signing, or TestFlight behavior.

### Class B — physical-device development

- Use an authorized physical iPhone in the approved iOS 26 point-release matrix, including the product-floor cell, and an authorized containing-app proof target with the development entitlement.
- Keep development-only verifier records, Apple endpoints, AAGUID policy, receipts, signing material, storage keys, routes, and evidence isolated from TestFlight/production-class proof state.
- Allow only the exact Apple and disposable proof-verifier routes approved for the case; deny every production Hezo route, credential, data store, and cross-plane service.
- Store private identifiers, entitlements, device/build details, raw artifacts, routes, and logs outside Git.
- Reset app-local and verifier state according to each lifecycle case without inferring a stable device or installation identity.

### Class C — physical-device distribution

- Use an authorized restricted internal TestFlight build on a physical iPhone in the approved iOS 26 point-release matrix, including the product-floor cell; external testers are out of scope.
- Treat App Attest as production because Apple does, regardless of the source entitlement value. Keep every Hezo-controlled service, credential, database, key, route, and dataset disposable and proof-only.
- Use production-only App Attest proof records and environment-matched Apple endpoints; reject every development artifact and prevent any store, credential, key, fixture, or policy interoperability.
- Obtain privacy-counsel approval before installation and keep O-010 open for external/public scope.
- Record exact OS, Xcode, SDK, signed-build, contract, policy, verifier, parser, crypto, and Apple-source observation revisions in restricted evidence; publish only safe version classes and opaque references.

The current evidence schema can label `physical_device_development` and `physical_device_distribution`, but each case has one environment reference, its network-mode vocabulary does not explicitly name development Apple service calls plus an isolated verifier, and every environment asserts no production credentials. Before execution, the schema/companion contract must define truthful client/verifier composition and network-mode mapping and distinguish Apple production-environment signing from a prohibited Hezo production credential; if the existing fields cannot state the run truthfully, update and review the schema rather than mislabel evidence. Optional production receipt-risk refresh cannot be represented by silently setting the credential field false; either approve an accurate schema/companion mapping or keep that branch disabled.

Every class has preauthorized request, elapsed-time, storage, concurrency, rate, retry, log, and cost ceilings; an allowlist of network contacts; per-case typed contact counters; a reset receipt; and an owner-controlled emergency stop. A static scan or policy promise is not evidence that isolation held.

- execution begins without the exact approved plan, prerequisite, fixture, environment, device, signing, privacy, evidence, or owner state;
- a production Hezo route, credential, identity, dataset, store, or operational dependency is contacted or required;
- a raw Apple/device/signing/security artifact, secret, identifier, semantic body, personal datum, live target, or private evidence location enters Git or an unapproved sink;
- App Attest runs in or passes material to the URL Filter extension or another unauthorized process;
- development material is accepted as production, production material is accepted as development, or environment-specific credentials, stores, fixtures, policies, keys, backups, or records interoperate;
- any malformed chain/nonce/key/App-ID/AAGUID/counter/receipt/extension/signature input, body/method/route/purpose/version/environment substitution, replay, equal/lower counter, or expired/revoked state is accepted;
- challenge/counter/capability/effect state is non-atomic, concurrency yields more than one winner, lost-response recovery mints or applies more than one authority/effect, or idempotency returns a result for another request;
- an assertion/capability exposes or forwards an App Attest key, stable subject, raw IP derivative, cross-plane trace, semantic body, MPD/analytics value, or joinable replay identity;

- execution actually uses, accepts, or relies on a material Apple source, OS/SDK, tool, contract, fixture, signed artifact, environment, or topology that differs from the approved plan; a newly announced external change detected before the affected observation and with no safety failure is classified only by the Inconclusive rule below.

Contain by halting requests, retries, rollout, TestFlight access, proof endpoints, and metered resources; revoking proof credentials/capabilities; isolating affected state; preserving only policy-permitted restricted evidence; privately escalating to the accountable security/privacy/Apple roles; and executing `S0-C-CASE-900`. App Attest-dependent write/influence work remains paused until a revised plan is approved and rerun. A Stop is useful kill-risk evidence and never a Pass.

### Inconclusive outcome

An already-authorized run is Inconclusive only when a required result is genuinely undecidable because of a transient external condition and there is no evidence of a safety, authorization, plan-integrity, or evidence-integrity failure—for example, Apple/TestFlight/proof service is temporarily unavailable; a device lifecycle result is confounded by unrelated platform state; the observer cannot distinguish absence from missing instrumentation; a frozen Apple source/SDK changes before the affected case can execute; the independent implementation or intact approved evidence becomes temporarily inaccessible; or a permitted sandbox AAGUID or receipt-contract contradiction cannot be resolved and genuinely blocks a required observation for the tested release. The universal extension-support conflict is a documented non-gating limitation for S0-C's static artifact boundary and cannot drive the root outcome. Outcome precedence is closed: any observed invariant failure, actual use of an unapproved material revision, proof-caused missing/corrupt evidence, prohibited disclosure, or unsafe state is Stop; only the no-failure transient conditions just listed are Inconclusive.

Missing authority, contracts, fixtures, runner, device, signing, privacy review, or evidence location before execution leaves the plan Draft, not Inconclusive. After an inconclusive run, complete `S0-C-CASE-900`, preserve the limitation, revise and reapprove the plan/matrix, reset all affected state, and rerun. Physical-development success, offline-vector success, or a partial TestFlight flow is never rounded up.

## Limitations and unsupported claims

- App Attest does not identify a person, unique human, durable physical device, or uncompromised OS/device.
- It does not prove a URL/report true, a destination safe, a verdict correct, or an operation entitled to bypass semantic validation, rate limits, or source policy.
- One key is installation scoped for this purpose; update observations do not prove continuity across reinstall, migration, restore, transfer, or key loss.
- Subjectless capability output is not anonymous or cryptographically unlinkable and retains issuer/destination timing-correlation limits.
- App Attest does not replace Privacy Pass, PIR, MPD, a blinded measurement credential, or reinstall deduplication. Apple fraud-risk values and key counts are not MPD.
- Unsupported or unavailable App Attest is not proof of fraud and cannot disable core read-only protection.
- Direct-Xcode, Simulator, mock, parser, or offline-vector success cannot prove TestFlight production App Attest. TestFlight proves Apple production environment behavior only, not Hezo production infrastructure, URL Filter routing, or release approval.
- A syntactically valid object, entitlement visibility, Apple documentation, submitted external request, or single positive case cannot prove full verifier correctness or replay resistance.
- Production counters need only be strictly increasing, not consecutive.
- The proof does not claim all extension types support or reject App Attest; it enforces only Hezo's containing-app/URL-Filter boundary.
- The signed minimal URL Filter artifact inspection does not prove system activation or a future product extension's runtime behavior. S0-B and the later release gate must exercise the implemented extension through Apple's supported system path and rerun the boundary checks; S0-C does not consume O-005 merely to create runtime evidence.
- The frozen iOS 26/newer matrix cannot establish future Apple service, OS, SDK, AAGUID, extension, receipt, field, rate, or availability behavior. Evidence expires on a material change and must be rerun.
- Dynamic Apple guidance is not a quota, capacity reservation, or SLA. This proof makes no performance, availability, fraud-prevention, security-certification, privacy-compliance, launch, or marketing claim.
- A Pass does not implement or approve S0-B, S0-D, S0-E, S0-F, Stage 0, Stage 1, report intake, measurement, production APIs, App Store submission, external beta, or public release.

## Teardown or productionization

The default for Stop or Inconclusive is **Teardown**. Owner-controlled closeout stops eligibility, challenge, registration, assertion, capability, receipt-refresh, retry, rollout, and scheduled traffic; disables proof routes/services and TestFlight access; revokes proof credentials, certificates, profiles, signing/JWT authority, capabilities, and test identities; marks keys revoked; removes app-local proof state; and deletes operational/transient challenge, counter, replay, capability, rate, receipt, verifier, log, capture, build, cache, replica, snapshot, backup, input, output, and evidence-working state under the accepted policy.
